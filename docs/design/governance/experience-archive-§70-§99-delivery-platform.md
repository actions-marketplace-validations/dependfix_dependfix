## 七十、M42 归档批次经验沉淀（测试断言真实性 / 外部工具语义 / 视觉基线连带 / 交付纪律）

> **批次**：M42 修复交付正确性 + 平台能力与体验补强（2026-10-11 归档）。以下 9 条已按 L1 / L2 / L3 三层收敛，规范落点与检查点矩阵行同步登记。

### 1. 交互断言的点击目标必须与组件事件绑定一致（e2e 弱断言与 flaky 的共同根因）

- **现象**：断言「点击表头排序」时点了表头单元格，而组件把点击绑定在单元格**内部**的按钮上 → 排序从未触发；断言却仍可能通过——接口默认按创建时间倒序返回，用例按序插入的数据使首行恰为「期望端点值」。
- **手法**：① 断言前先确认事件绑定元素（读组件模板：单元格只挂 `aria-sort`，触发器是内部按钮）；② 目标态必须**只能由目标行为产生**（用排序属性硬锁，未排序态为 `none` 必然失败）；③ 三态控件逐次点击并**等待属性回写**（异步渲染下立即读会读到旧值 → 多点击 → 状态过冲）。
- **落点**：[testing.md §6.5](../../standards/testing.md)（交互断言补充）+ 检查点矩阵行。

### 2. 与外部工具语义对齐的判定须用该工具权威实现逐形态实测

- **现象**：`.gitignore` 幂等判定的首版实现按书写直觉把「行中 `#`」当行内注释剥离，与 git 实际语义不符（git 仅把行首 `#` 当注释）→ 假命中 → 漏追加 → 报告目录可能随提交入库（**安全方向回归**）。
- **手法**：列形态清单（**含反例**）→ 用工具权威判定命令逐形态实测 → 与实现双向比对；等价类扩展倾向保守（宁可多报不可漏判）。
- **落点**：[development.md §5.1.40](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 3. 改动页面的视觉基线重建含「以该页为背景」的连带面

- **现象**：页头加一个按钮 / 改 flex → 整页基线失配（预期）；**另有弹窗内浮层的视口级基线同样失配**（其取景包含该页背景）。
- **手法**：改动页面后列出该页相关的全部基线（整页 + 视口 + 元素级），逐个判断是否需重建；重建用 `--update-snapshots=all` 并连跑两遍验证幂等；无视觉守卫的页面显式登记。
- **落点**：[testing.md §6.7](../../standards/testing.md)（扩展）+ 检查点矩阵行。

### 4. 验证同进程服务时不得用同步子进程调用

- **现象**：用 `spawnSync` 拉起被测工具去验证「本进程内的拦截代理」→ 同步调用阻塞事件循环 → 代理无法 accept → 记录为空 → 误判「代理未生效」。
- **手法**：改用异步 `spawn` + 等待退出；配合**同环境反例对照**（旧配置再跑一次）证明代理确实被使用且修复确实生效。
- **落点**：[testing.md §6.10](../../standards/testing.md)（新条款）+ 检查点矩阵行。

### 5. ESM 接线断言用「部分 mock + 委托真实实现」

- **现象**：ESM 下无法用 spy 断言「A 以某实参调用 B」；整体 mock B 又会破坏依赖 B 真实行为的既有用例。
- **手法**：`vi.mock` + `importOriginal` 保留其余导出、仅包装目标函数（记录实参后**委托真实实现**）；实参容器由 `vi.hoisted` 提供，用例断言后于 `beforeEach` 清空。
- **落点**：[testing.md §6.6](../../standards/testing.md)（扩展）+ 检查点矩阵行。

### 6. 删除公共导出前必须全仓 grep（含全部测试目录）

- **现象**：删除工具函数导出时只查了源码与同目录测试，漏掉集中测试目录 → `typecheck` 报 TS2305。
- **手法**：不带路径限定的全仓检索 + 区分代码引用与文档描述性文本；测试文件按「同目录 + 集中目录」双份核对；核验引用面时注意 `rg -r` 是替换陷阱（输出被替换成假象）。
- **落点**：[development.md §5.1.39](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 7. 同批同源断言必须全仓一次改净

- **现象**：同一批在多个文件写入同一 `file:line` 断言，修复时只改了其中一处 → 审计判「同源残留」。
- **手法**：修复任一处后用旧值全仓复核；跨文件同源写入是该规则的另一个变体。
- **落点**：[planning.md §4.4 第 13 条](../../standards/planning.md)（扩展）+ 检查点矩阵行扩展。

### 8. 阶段状态口径翻转的同步面含各文档速查表

- **现象**：阶段启动 / 归档时把「暂无进行中阶段」翻转为「Mxx 进行中」，漏改某文档的速查表 → 自相矛盾，且批次记录中「口径已同步」的声明失实。
- **手法**：列出全部承载位置（待办速查表 / 路线图指针 / 各文档速查表 / 首页里程碑）逐处同步。
- **落点**：[documentation.md §6](../../standards/documentation.md)（扩展）+ 检查点矩阵行。

### 9. 入口脚本（PID 1 / 子进程编排）用真实 shell + PATH 桩做脚本级测试

- **现象**：root 降权 / 子进程看护 / 信号处理等编排逻辑难被 TS 单测覆盖，但属可靠性关键路径。
- **手法**：`sh` 直驱脚本 + 经 `PATH` 注入桩命令（`id` / `sleep` / `date`）重塑环境（降权分支、即时退避、时间快进）；断言基于输出流与进程存活探测；Windows 用 `describe.skipIf` 跳过。
- **落点**：[testing.md §6.10](../../standards/testing.md)（新条款）+ 检查点矩阵行。

## 七十一、M43 归档批次经验沉淀（收窄改动语义 / 注入时机 / 门禁与脚本单测 / 覆盖面声明）

> **批次**：M43 PR Check 能力补强 + 运行时可靠性与工程治理（2026-10-14 归档；含阶段期间 caomei-ui `0.6.0` 升级回归插队热修）。**准入依据**：各条满足 [experience-archive.md 文件头](./experience-archive.md) 准入标准之一（可执行方法论尚未迁移到规范 / 决策需溯源 / 同类问题复现 ≥ 2 次 / 工具与环境陷阱），落点见各条目末行。以下 7 条已按 L1 / L2 / L3 三层收敛，规范落点与检查点矩阵行同步登记。

### 1. 「收窄 / 跳过」类改动必须先穷举被跳过步骤产物的消费者

- **现象**：为省成本 / 消除假失败而**整段跳过**某流水线步骤，该步骤的产物却同时被别处当判据 → 无关路径语义退化：零告警仓库的「处理成功」信号原由收尾验证链的 `verificationPassed` 承载，跳过使「健康零告警仓库 + 真实失败仓库」的多仓运行由 exit 1 退化为 exit 2（恰好是该批次要消除的误归因形态）。
- **手法**：按**字段级**穷举被跳过步骤产物的全部消费者；把跳过后的判据空洞显式补上（新增信号，或跨用例不变量锁定）；审计此类改动先问「被跳过的步骤是否还在别处产出判定依据」。
- **落点**：[development.md §5.1.41](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 2. 可注入 composable 的缺省实现必须在 setup 期解析 setup-only 依赖

- **现象**：为可测性引入 `useXxx(deps)` 时，缺省实现写成延迟求值的缺省参数 → `useI18n()` 在事件处理期被调用（setup-only composable）→ 抛错被 handler 的 try/catch 吞掉 → **三条分支（合并 / 成功 / 失败）全部静默失效**；注入桩的单测不复现、`typecheck` / `lint` 均 0 报错。
- **手法**：缺省分支用 `deps.x ?? resolveXxx()`，`resolveXxx()` 在 setup 期求值一次并闭包持有；事件期只调 event-safe 全局（`$fetch` / `navigateTo`）。检出手段是**既有 e2e 全量复跑**（失败用例表现为超时而非断言失败）。
- **落点**：[development.md §5.1.42](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 3. 门禁 / 脚本类单测的两个 mock 语义陷阱

- **现象**：① 早返回分支只写 `process.exit(0)` 时，测试环境（`process.exit` 被 mock）会继续落到后续逻辑 → 「删除该分支副作用」的 mutation **存活**（自检阶段一度漏杀）；② 为 `scripts/**` 写单测时，夹具里写入会被该脚本判定的字面量（规划编号形态）→ 门禁在**源码层**命中自己；夹具 token 若与其所在行被拼接成一行，`it(...)` 作为测试名单元不做引号感知 → 必命中。
- **手法**：早返回处 `process.exit` **兼** `return`；夹具用运行时拼接构造 token（不写字面量），或依赖「行尾注释提取会跳过字符串字面量」的特性。
- **落点**：[testing.md §6.11](../../standards/testing.md)（新条款）+ 检查点矩阵行。

### 4. 规范 / 文档的「覆盖面」声明必须带作用对象限定

- **现象**：声明「push 侧全部 4 处推送调用点」时未限定作用对象 → repo-wide 阅读被理解为「零遗漏」，而 `scripts/**` 的发布辅助脚本同样执行 `git push`（其作用对象是工具自身而非被修复仓库）；审计据此追问并判 warning。
- **手法**：覆盖面声明限定**作用对象**并显式列出**不适用面**；声明前先 `rg` 穷举并按作用对象分组。
- **落点**：[documentation.md §6](../../standards/documentation.md)（扩展）+ 检查点矩阵行。

### 5. 文档示例与实现不一致时优先补实现侧的容忍

- **现象**：文档给出的摘要行示例（裸 `→ <target>`）实现未捕获（正则要求 `→ 详见/已迁移至` 前缀）→ 按文档字面书写时 `target` 恒为 `null`；同形问题还表现为历史区条目整段未被识别为「已蒸馏条目」。
- **手法**：若该形态属**既有文档已声明的约定**，在实现侧扩展容忍并补测（本次顺带使历史区条目开始携带 target）；把文档改窄会把已存在的既有数据形态判为「不支持」。
- **落点**：[documentation.md §6](../../standards/documentation.md)（同一扩展的第二点）+ 检查点矩阵行。

### 6. complement-stash 多 commit 隔离的两个操作性陷阱

- **现象**：① `git add -N`（intent-to-add）的新文件让 `git stash push` 报 `Entry … not uptodate. Cannot merge` → 隔离失败；② 隔离脚本无 EXIT trap 时，commit 被 commitlint 拒绝后 `set -e` 在 `git stash pop` 之前退出 → 补集改动**滞留 stash**（本次实测踩中一次，靠 `git stash list` + `git stash pop` 人工恢复）。
- **手法**：stash 前对 intent-to-add 文件先 `git reset -- <path>` 退回未跟踪；隔离脚本用 `trap restore EXIT` 保证失败路径也恢复补集。
- **落点**：[git.md §3.7.1](../../standards/git.md)（扩展）+ 检查点矩阵行扩展。

### 7. 语义变更必须连带同步同源声明（JSDoc / 注释 / 同源断言）

- **现象**：`hasGitChanges` 改为「非仓库返回 false」后，同函数族的门禁 JSDoc 仍写「回滚失败（如非 git 目录）追加 `ROLLBACK_FAILED`」——与新守卫（非仓库在回滚之前短路）矛盾；审计判 warning（属该批次 AC 明列的同步项）。
- **手法**：语义变更时按**同源面**扫描并同步：实现旁的 JSDoc / 注释、引用该语义的测试名与测试注释、以及同族函数的交叉引用；「被替换的旧触发条件」是最高频漏点。
- **落点**：[development.md §5.1.41 / §5.1.42](../../standards/development.md) 对应的两条检查点矩阵行（本条不单独开条款），并以本条 7 的现象清单作为「同源面」枚举模板。

## 七十二、入口脚本信号处置顺序与「本地不可复现偶发红」的取证路径

> **批次**：M44 阶段期间插队热修（entrypoint 双进程信号处置顺序竞态，按插队例外清单第 3 类「CI 主链路阻塞」+ 用户授权处置）。**准入依据**：④ 工具 / 环境陷阱（缺陷只在本机不可复现的调度下出现）+ ② 决策需溯源（「就绪行严格晚于处置安装」属容器停止语义的约定）。落点见各条目末行。

### 1. 就绪行必须晚于信号处置安装（观测方同步点唯一性）

- **现象**：容器入口脚本先打印「进程 pid」就绪行、后安装 TERM / INT 转发 trap → 以该行同步发停止信号的观测方（容器编排 / 健康检查 / 行为测试）可能落在窗口内，内核按默认处置终止 PID 1：退出码为 signal 终止而非约定值，看护循环与 worker 亦短暂失去父进程。
- **手法**：把「对外可观测的就绪声明」与「进程编排已就绪」绑定为同一顺序不变量——先装 trap，再启动子进程，最后打印就绪行；主进程尚未启动时补 fail-safe 退出（防吞掉停止信号后照旧启动）。
- **落点**：[platform.md §10.6](../../standards/platform.md#106-队列执行进程隔离独立-worker-进程)（严格约束 + 已知边界 ⑤⑥）+ 检查点矩阵行 + L1 源码顺序断言（`apps/platform/docker/entrypoint.test.mjs`）。

### 2. 偶发红的取证路径：重跑定性 → 负例标定 → 静态守卫固化

- **现象**：同一 commit、同一 runner 镜像下同一用例时而通过时而报 signal 终止；本机定向探针与全量测试均不复现——「本地不可复现」本身不能作为「无缺陷」的依据。
- **手法**：① 先**重跑失败 job 定性**（同镜像同 commit 重跑即绿 → 判定偶发而非回归，避免误改）；② 再按机制假设做**负例标定**放大窗口（把 trap 放回就绪行之后 + 用绝对路径 `sleep`，绕过 PATH 桩）→ 复现出与 CI 完全一致的退出形态；③ 对只在特定调度下出现的竞态，用**源码顺序断言**（L1）替代不可稳定复现的运行期断言；④ 运行期断言携带 `signal` 字段与失败消息，使同类失败一次定位。
- **落点**：[testing.md §6.10](../../standards/testing.md)（扩展：就绪行同步点断言 + 桩命令屏蔽陷阱）+ 对应检查点矩阵行扩展。
